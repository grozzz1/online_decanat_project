# Типы документов и извлечение полей

Три типа определены в одном реестре `utils/document_fields.py`:

| ID | Название | Полей |
| --- | --- | --- |
| `study_certificate` | Справка об обучении | 10 |
| `academic_leave_application` | Заявление на академический отпуск | 8 |
| `internship_certificate` | Справка о практике | 10 |

Реестр используется схемами извлечения, шаблоном сайта, backend и Telegram-клавиатурами.
В отправке документа доступны академический отпуск и справка о практике;
в вопросе по документу, backend, OCR и боте поддерживаются все три типа.
Выбор не сбрасывается при переключении режимов. Исходный академический отпуск
остаётся выбранным по умолчанию; оформление `select` сохранено.

## Данные и совместимость

Форма по-прежнему отправляет `application_type`, теперь со стабильным ID.
Backend принимает также прежние русские названия. Маршруты не переименованы.
В ответе `/api/messages` старое `application_type` остаётся русским названием,
а новые поля `document_type`, `fields`, `extraction` добавляются к существующим.
OCR-текст, CV-результаты, исходные документы, просмотр страниц PDF и авторизация сохранены.

`analyze_document()` / `analyze_document_async()` теперь дополнительно возвращают:

```json
{
  "document_type": "academic_leave_application",
  "fields": {
    "student_name": null,
    "group": null,
    "course": null,
    "leave_reason": null,
    "leave_start": null,
    "leave_end": null,
    "application_date": null,
    "student_signature": null
  },
  "extraction": {
    "document_type": "academic_leave_application",
    "document_label": "Заявление на академический отпуск",
    "fields": {},
    "field_statuses": {},
    "errors": []
  }
}
```

В примере вложенные словари сокращены: в реальном `extraction.fields` находятся
те же значения, что в `fields`, а `field_statuses` содержит статус каждого поля.
Выбранный тип теперь хранится отдельно в `selected_document_type`. Если он не передан,
но классификация уверенно установила фактический тип, извлечение всё равно выполняется.
Если неизвестны оба типа, OCR/CV выполняются, `document_type=null`, `fields={}`, `extraction=null`.

Текстовые поля — строки или `null`, `course` — целое число или `null`.
Даты — ISO `YYYY-MM-DD` или `null`. Подписи/печати — `true`, `false` или `null`:

- `true`: CV вернул достаточно уверенный визуальный кандидат; для подписи студента
  дополнительно необходима роль `student` из OCR-контекста.
- `false`: анализ всех страниц завершён и соответствующий элемент не обнаружен алгоритмом.
- `null`: CV недоступен, результат сомнительный, роль неизвестна или анализ неполный.

Надписи «подпись» и «печать» в OCR сами по себе не дают `true`.
`true` не является подтверждением подлинности, `false` не доказывает фактическое отсутствие.

Статусы полей:

| Статус | Значение |
| --- | --- |
| `found` | Однозначное значение извлечено / визуальный кандидат обнаружен |
| `missing` | Значение не найдено / CV не обнаружил элемент после завершённой проверки |
| `unknown` | Проверить или распознать значение не удалось |
| `ambiguous` | Найдены несколько разных значений; значение возвращено как `null` |

## Regex и валидация

Обработка нормализует Unicode, пробелы, переносы строк, `ФИ0`, некоторые OCR-ошибки
цифр даты. Поддерживаются подписанные поля с двоеточиями/тире, несколько полей
на одной строке, перенос значений, некоторые обычные формулировки справок.
ФИО студента и руководителя извлекаются по разным ориентирам.

Принимаются даты `DD.MM.YYYY`, `DD/MM/YYYY`, `DD-MM-YYYY`, `YYYY-MM-DD`
и русские месяцы, например `«1» октября 2026`. Календарные даты проверяются:
`31.02.2026` не превращается в значение. Короткий год не угадывается.
Даты рождения или другие неподписанные даты не назначаются датой выдачи/заявления.
Интервалы «с ... по ...» учитываются только рядом с контекстом обучения,
академического отпуска или практики, соответствующим выбранному типу.
Если несколько разных кандидатов относятся к одному полю, возвращается `null`.

В репозиторий добавлено предоставленное вымышленное `rules.md`. Теперь:

- проверяется соответствующая схема и порядок начала/окончания её периода;
- пропуски, неизвестные и неоднозначные поля перечисляются в `validation.fields.issues`;
- перевёрнутый период получает `reversed_period`; даты сохраняются без перестановки;
- обязательные поля и источники берутся из разделов 3–5 Положения;
- `validation.completeness` содержит предварительный статус и ссылки на пункты;
- окончательное принятие документа не автоматизируется. При несовпадении типов
  сайт сохраняет файл/OCR и предлагает сменить выбор либо сразу отправить с выбранным
  типом жёлтой кнопкой. Во втором случае сервер сохраняет `type_mismatch_confirmed=true`
  и извлекает/проверяет поля по выбранной схеме, сохраняя независимый результат классификации.
  Неизвестный тип не требует подтверждения расхождения.

## Логи

`utils/document_logging.py` использует стандартный `logging`, logger
`decanat.documents`, и существующий `bot.write_log` для терминала и Telegram-чата журнала.

- INFO — все поля найдены.
- WARNING — есть отсутствующие, неизвестные или неоднозначные поля.
- ERROR — возникла ошибка OCR, координат OCR, CV или извлечения.

Каждый отчёт включает тип, источник, число ожидаемых и найденных полей,
статус всех полей, списки отсутствующих/неизвестных и типы ошибок.
Значения полей и текст исключений в отчёт не включаются. При ошибке OCR
все поля остаются `null` со статусом `unknown`; сайт отмечает обращение как `failed`,
а Telegram-бот позволяет повторить отправку. Ошибка извлечения не мешает пересылке
успешно распознанного документа, но отражается в отчёте.

Полный OCR-текст исключён из audit-лога сайта. В существующем журнале сообщений
бота содержимое сообщений при обработке документа скрывается, чтобы пересланный
в деканат OCR не обходил это ограничение. Сам текст остаётся доступен владельцу
на сайте и передаётся деканату как раньше. Существующее скрытие токена/кодов входа сохранено.

## Запуск и проверки

Новых зависимостей эта доработка не добавляет. Перезапустите `python main.py`.
Установка зависимостей и Tesseract описана в [DOCUMENT_CV.md](DOCUMENT_CV.md).

```powershell
python -m unittest discover -s tests -t . -v
```

Автоматические тесты включают прежние проверки CV/PDF и новые сценарии:
все поля всех трёх схем, отсутствие/неоднозначность данных, варианты дат,
переносы строк, разные периоды, отрицательный/сомнительный CV, INFO/WARNING/ERROR,
отсутствие персональных значений и секретов в новых отчётах, оба режима сайта,
совместимость русских названий, классификацию, исправление типа без повторного OCR,
явное подтверждение, обработку ошибок OCR и повторную отправку,
все три типа в Telegram, неподдерживаемый файл, ссылку и авторизацию.

Браузерная проверка:

```powershell
python -m pip install -r requirements-dev.txt
python -m tests.browser_visuals
```

В Chrome проверены три варианта списка, сохранение выбора между режимами,
фактическая отправка каждого типа с сайта и результат backend, ссылка на бота,
а также прежние PDF, подсветка, масштабирование и узкий экран.
OCR и Telegram в регрессионных проверках заменены подставленными результатами;
реальные сообщения не отправляются.

## Ограничения и файлы

Regex не покрывает все свободные формулировки и ошибки OCR; неподдержанный,
нечитабельный или противоречивый текст может давать `null`. Реальной размеченной
выборки трёх типов в проекте нет, точность на настоящих документах не измерялась.
Существующие ограничения CV и хранения в памяти остаются прежними.

Новые файлы: `utils/document_fields.py`, `utils/document_logging.py`,
`tests/test_document_fields.py`, `DOCUMENT_FIELDS.md`.

Изменены: `utils/keyboards.py`, `utils/ocr.py`, `utils/validation.py`,
`utils/bot.py`, `utils/delivery.py`, `handlers/menu.py`, `handlers/requests.py`,
`webapp/app.py`, `webapp/service.py`, `webapp/store.py`,
`webapp/templates/index.html`, `webapp/templates/login.html`,
`webapp/static/app.js`, `webapp/static/style.css`,
`tests/test_document_integration.py`, `tests/browser_visuals.py`, `DOCUMENT_CV.md`.
